# Memories

## Problem & Why

A family photographs two very different kinds of things in FamilyHub: a savings-goal occasion (a trip, a birthday — something planned and funded ahead of time, `events` with `is_occasion=true`, see `supabase/migrations/0019_occasions_optional_money.sql`), and an everyday expense receipt (a restaurant bill, a purchase — logged with no goal behind it at all). Both produce photos worth browsing later, and the product wants one unified "everything we photographed" surface — a calendar with photo-dot days, a chronological timeline, and an album grid — regardless of which of the two origins the photo came from.

The complication is that these two origins live in genuinely different tables with no natural join: goal-linked photos are `event_memories` rows (captioned, attached to an `events` id), while expense photos are `transaction_photos` rows attached to a transaction. Earlier, the only way an expense photo reached the Memories surface was by mirroring the expense into a synthetic "achieved event" (see Architecture below) — a bridge that turned out to drop photos in production (`supabase/migrations/0015_event_source_txn.sql`, `0029_backfill_mirror_events.sql`). `src/js-ui/40-memories.js` is the reconciliation layer that solves this: it builds one in-memory feed, `memRecords`, that both origins feed directly, and every rendering surface (calendar, timeline, album, single-photo viewer) reads from that one feed instead of walking `events`/`transactions` separately.

## Architecture & How It Works

### The two origins, and the bridge between them

- **Occasion memories** — `event_memories` rows (schema: `supabase/migrations/0001_schema.sql:186-200`), captioned photos attached to an `events` row. An event only surfaces here once it's in the past or explicitly marked `achieved` (`achievedNow()`, `src/js-ui/10-nav-model.js:53`) — a planned future occasion belongs in the "Sắp tới" (upcoming) list, not in memories.
- **Expense photos** — `transaction_photos` rows, hydrated onto `window.txns[i].photos` as an array of URLs. Any expense can carry photos regardless of whether it's tied to a goal.
- **The mirror-event bridge** — `syncExpenseEvent(t)` (`src/js-ui/40-memories.js:107-123`). Any time a transaction's `photos` array becomes non-empty, this function writes (or updates in place) a synthetic `events[key]` row tagged `fromExpense: t.id` and `_srcTxn` (bound durably server-side via `events.source_txn_id`, added in `supabase/migrations/0015_event_source_txn.sql`), with `achieved:true` and `memories` built straight from `t.photos`. If the transaction's last photo is removed, the mirror event is deleted (`:120-122`). This exists **so the expense also has a row in `events`** — which is what powers "Open expense" from a memory (`_renderMemoryDetail`, `40-memories.js:424`), the durable link that survives a photo being re-added, and (historically) the Events tab list. `renderEvents()` (`src/js-ui/30-events-render.js:52-59`) explicitly filters mirror events (`_srcTxn`/`fromExpense`) out of the Events tab display — the mirror is still created under the hood, only its display there is suppressed.
  - Called from four places, all after a transaction's `photos` array changes: `addExpense` (`src/js-ui/60-transactions.js:250`), `saveExpenseEdit`'s photo add/remove/reorder path (`src/js-ui/55-expense-photos-writes.js:188,318`), the bulk photo-assign flow `paApply` (`src/js-ui/55-expense-photos-writes.js:349`, wired through `55-expense-photos-writes.js:170-190`), and the write-through wrapper in `src/js-data/50-writethrough-realtime.js:36` which persists whatever mirror event the local call spawned.
  - The mirror-event upsert has been a recurring source of bugs: `0015_event_source_txn.sql` added `source_txn_id` after clones were observed in production (one $50 expense had spawned 3 events and 3× $50 budget fundings); `0029_backfill_mirror_events.sql` records that the write-through's `ON CONFLICT('source_txn_id')` upsert silently failed against the partial unique index (Postgres error 42P10) for a stretch, so **no mirror event was created at all** for expense photos added during that window, swallowed by the client's generic error handler. That migration's own comment is the clearest statement of where this is headed: *"The app itself no longer depends on this for display (Memories/the calendar now read photos straight off `transactions`/`transaction_photos`)... This backfill just brings the database's mirror-event bookkeeping back in line with what it should have recorded all along, for any feature that still expects one to exist."*

### `buildMemRecords()` — the single source of truth

`src/js-ui/40-memories.js:124-152`. Rebuilds `window.memRecords` (newest-first) from scratch on every call. The function's own comment names it explicitly:

> `// EXPERIMENT (unify "memory"): a memory is any photographed moment in the past — whether it hangs off an event (a savings goal) or an expense. So the feed is built from two sources directly, and no longer relies on the mirror-event bridge to surface expense photos.`

It merges two sources, with a deliberate skip to avoid double-counting:

1. **Real events** (`:134-140`) — walk `order` (the events display order), skip anything that isn't a real occasion (`e._srcTxn || e.fromExpense` → mirror event, skipped here) and anything not yet achieved, then push one `memRecords` entry per `event_memories` item (`e.memories[]`), tagged `type:'event', ref:<event key>`.
2. **Mirror events are explicitly skipped at read-time** (`:135`, `// mirror event → handled via its expense below`) — this is the double-counting guard. A photo-expense's mirror event does carry its own `memories[]` (built by `syncExpenseEvent` from `t.photos`), but `buildMemRecords` does not read it.
3. **Every expense photo, read directly off the ledger** (`:141-150`) — iterates `window.txns`, and for every transaction with a non-empty `photos` array (excluding `t.future` proposals — a planned expense's photo is a preview, not a memory yet), pushes one `memRecords` entry per photo, tagged `type:'expense', ref:t.id`, dated via `txPhotoDate(t)` (EXIF capture date when available, else the transaction's date — `src/js-ui/50-sheets-expense-capture.js:721`, backed by `taken_on` added in `supabase/migrations/0018_photo_taken_on.sql`).

The two-source, skip-the-mirror design means an expense photo is never missed just because its mirror-event write failed or raced a hydrate — the fragility that motivated the rewrite (see the `0029` migration comment above). This is a **recently refactored, not-fully-settled area** — see Current State.

Every other rendering entry point in this file — `memCalInit()` (picks the calendar's initial month off `memRecords[0].d`, `:3-10`, itself explaining why it can't just look at the latest event: "otherwise this lands on the month of the latest EVENT memory even when the real latest activity is an expense photo with no mirror event"), `renderMemCalendar()`'s photo-dot days (`:31-70`), `renderMemoriesTab()`'s month grid (`:355-370`), and `openPhotosForDate()` (`:372-381`) — calls `buildMemRecords()` fresh and reads only `memRecords`. There is no cached/derived state that could drift from the two origins.

### Calendar and the day-tap prompt

`memCalInit()`/`renderMemCalendar()` (`:1-70`) render a month grid where any day with at least one `memRecords` entry gets a photo tile (background-image from the first record's `.src`, or a category-emoji tile if the record has no photo). Empty days render as a focusable `<button>` (`:59-66`, accessibility fix noted inline — photo cells predate this and stay `<div>`s).

Tapping an empty day doesn't jump straight to a form. It sets `mcalSel` (a plain variable, not DOM state — the comment at `:71-76` explains this choice: a hydrate's re-render on focus/realtime/write must not silently clear the selection) and reveals an inline prompt (`renderMcalPrompt()`, `:83-96`). `mcalPick(y,m,d)` (`:77-81`) toggles the selection on a second tap.

The prompt's action is decided purely by the date, not by asking the user: `dt.getTime() < TODAY.getTime()` (`:90`) — a past day can only offer **"Log an expense"** (`openExpense({date:iso})`), a future day can only offer **"Plan an event"** (`openEventModal({date:iso})`). `mcalCreate()` (`:97-103`) dispatches on this and clears `mcalSel` "behind the modal, not on return" so the calendar doesn't flash a stale selection. Both entry points are defined in `src/js-ui/50-sheets-expense-capture.js:49` (`openEventModal`) and `:75` (`openExpense`) — see `docs/features/expense-capture.md`.

### Reactions surfaced onto memories

`src/js-ui/40-memories.js:216-297`. A photographed expense *is* a memory, and that same expense already carries the family's reactions (`t.reactions`, keyed by `_dbId`). `memTxFor(r)` (`:224-229`) resolves a `memRecords` entry back to its underlying transaction: directly for `type:'expense'`, or via `events[r.ref].fromExpense` for a `type:'event'` record whose event happens to be a mirror (`// safety: a mirror event's source expense`). For a real occasion — an `event_memories` photo hanging off a genuine savings-goal event with no linked expense — `memTxFor` returns `null`, and **no reactions surface**, because reactions are transaction-scoped only. This is a hard constraint, not a bug: see `docs/features/social-alignment.md` for how reactions are modeled and thrown (`throwReaction`, `RX`, `_rxFace` from `src/js-ui/62-reactions.js`) — this doc only notes where that constraint bites.

Three rendering weights reuse the same resolved reactions: `memRxClusterHTML()` (`:230-240`, passive emoji+face cluster on an album block), `memRxLineHTML()` (`:241-256`, one un-grouped row per reaction under a timeline card, capped at 3 with a "+N more"), and `memReactionsHTML()` (`:259-277`, the full list + a live react bar inside the memory detail overlay). `memReact()` (`:280-284`) throws a reaction on `curMemory`'s resolved transaction; `renderMemoryIfOpen()` / `renderMemoriesTabIfOpen()` (`:286-297`) keep the open overlay and the album's clusters live when a reaction arrives over realtime.

### Grouping, collage layout, and the two "photos by day" screens

- `memGroups()` (`:155-164`) clusters `memRecords` by `type:ref` into cover+items groups (used by the home carousel).
- `collageClasses(n)` (`:176-197`) picks a fixed template for ≤4 photos and a row-packing algorithm for 5+ so the grid never has empty cells (a "3+1" tail is rewritten to "2+2").
- `photoSectionsByDate()` (`:314-331`) is what `renderMemoriesTab()` renders: one section per calendar date, one captioned collage per event/expense inside it, plus an uncaptioned "everyday moments" bucket for anything without a `type`.
- `photoSectionsByEvent()` (`:333-354`) is what `openPhotosForDate()` renders instead: the same day's photos grouped by event/expense with a tappable title (deep-links to `openEvent()` or `openExpenseDetail()`), plus an "Everyday moments" section for the rest.

### `openMemory()` / `_renderMemoryDetail()` — the shared viewer

`:387-427`. Both the timeline and the album grid call `openMemory(i)` with an index into `memRecords`. It sets `curMemory` and, importantly, `curEvent`: for a `type:'event'` record, `curEvent = r.ref` directly; for a `type:'expense'` record, it resolves the transaction and takes `t.linkedEvent` (the mirror event, if one exists) — because zoom (`openPeek`) and delete (`deleteMemoryPhoto`) index against `events[curEvent].memories`, which carries the `_txn` pointer those functions need. The comment at `:389-392` calls this out directly: rendering the photo stack from `events[curEvent].memories` "keeps each tapped index aligned with what `openPeek()`/`deleteMemoryPhoto()` expect."

`_renderMemoryDetail()` (`:401-427`) is re-invoked after any photo delete so the stack stays honest. It picks the gallery list preferring `events[curEvent].memories` when available (`gal`), falling back to filtering `memRecords` by `type`+`ref` otherwise; renders each photo (or an emoji tile placeholder if `m.src` is empty); populates the reactions block only when `memTxFor(r)` resolves a transaction; and wires the single bottom action to either "Open expense" (`openExpenseDetail`) or "Open event" (`openEvent`) depending on whether the record itself, or its underlying event, is expense-backed.

## Current State

**This is an actively-evolving area, not a fully-settled design.** The `buildMemRecords()` function is explicitly marked `EXPERIMENT (unify "memory")` in its own source comment (`src/js-ui/40-memories.js:126`) — the two-origin merge with a deliberate mirror-event skip is a recent rewrite, not a long-stable pattern.

- **The mirror-event bridge (`syncExpenseEvent`) still exists and is still actively written on every photo-expense**, purely for backward compatibility: it's what makes `events.source_txn_id` durable (so "Open expense" from a memory detail, and the historical Events-tab presence, keep working) and what a hard-refresh's hydrate re-links (`src/js-data/30-hydrate.js:332-343`). But `buildMemRecords()` deliberately does not read the mirror event's own `memories[]` at display time — it goes straight to `transaction_photos` instead, which is the fix for the exact class of bug the mirror bridge produced (the 42P10 upsert failure documented in `supabase/migrations/0029_backfill_mirror_events.sql`, and the event-cloning bug documented in `supabase/migrations/0015_event_source_txn.sql`). **Watch for this split** when touching either function: a change to `syncExpenseEvent`'s write shape does not automatically show up in what memories the user sees, and vice versa — they are two independent code paths that happen to read the same `transactions.photos`.
- Because the mirror event is still created, there are effectively two representations of "an expense with photos" in memory at once (the mirror `events[key]` row and the raw `transactions[i].photos`) that must be kept consistent by convention, not by a single write path. `_renderMemoryDetail()`'s `curEvent` resolution (`:393-394`) and its comment (`:389-392`) are a direct symptom of this: the zoom/delete code still depends on the mirror event existing and being correctly linked.
- No test coverage exists for `buildMemRecords()`'s merge/skip logic; correctness currently rests on the inline comments and the migration history cited above.
