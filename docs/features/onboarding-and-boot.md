# Onboarding & App Boot

## Problem & Why

This doc covers two genuinely distinct concerns that happen to live in one source file, `src/js-ui/80-onboard-boot.js` (there is no evidence of a deliberate design reason for the pairing — it reads as organic growth: onboarding was the first thing in the file, boot/warm-start/SW-update logic was appended below it over time under the same `/* ---------- section ---------- */` comment convention used throughout `src/js-ui/`). The two halves don't share state or call into each other except at one seam (`obInit()` is called from the boot sequence, see below) and are best understood separately:

1. **Onboarding wizard** — a brand-new user has no family, no categories, no budget, and (for a create flow) no encryption key yet. The wizard is the only place in the app that walks someone through all of that in one linear sequence — name, family, starter categories, budget, theme — before handing off to `src/js-data/70-goals-income-onboard-ui.js` to actually write it to Supabase. A joining user takes a shorter path (redeem a code, set a profile) into an *existing* family instead.
2. **Boot orchestration** — every cold start of the PWA has to answer several questions before the first frame matters: is there a cached snapshot of this family's data to paint instantly (warm start), is the cache stale/instructive of a coming update, is there a service-worker update waiting, does a URL hash want to open straight into a specific screen, and is the device online. None of this is specific to onboarding; it runs for a returning signed-in user on every launch, including the ones who onboarded years ago.

The reason both matter architecturally: **this file is the origin point of data that the rest of the app takes for granted.** The default budget/category schema a new family sees for the rest of its life is decided here (`obPrefillBudget()`, see below) before `docs/features/budget.md`'s machinery ever runs. The encryption key material referenced throughout every financial write path (`docs/features/encryption.md`, `docs/features/key-card-auth.md`) is generated here, at `createFamilyInDB()` time, before a single transaction exists. Bugs or shortcuts taken at this layer don't stay local — they define the family's data shape and security posture from row one.

## Architecture & How It Works

### Onboarding wizard

**State.** A single global, `FAM` (`src/js-ui/80-onboard-boot.js:2-7`), accumulates everything the wizard collects — `user` (name/role/color), `familyName`, `mode` (`'create'` or `'join'`), `members[]`, `budget`, and (mid-flow only, create path) `catBudget`/`passcode`. Nothing is written to Supabase until the very last step; the whole wizard is an in-memory form.

**Step machine.** `obOrder` (`:10`) is the canonical step sequence: `welcome → locale → auth → choice → join|profile → family → budget → theme → done`. `obProg` (`:11`) maps each step to a progress-bar fraction (`:24-26` special-cases `profile` in the `join` branch to a fixed `.78`, since a joiner skips `family`/`budget` and needs the bar to read as "almost done," not proportional to `obOrder` position). `obGo(name)` (`:18-29`) is the only transition function — it toggles `.on`/`.past` classes on `.ob-screen` elements by comparing `obOrder` index, sets the progress bar width, and runs a couple of per-screen side effects (rendering the 6-digit join-code boxes, building the theme grid). There's no history stack or back-button state machine beyond what each screen's own "back" button hardcodes via `setAttribute('onclick', ...)` (e.g. `:61`, `:91`, `:190`) — the wizard is a flat sequence, not a graph, with a couple of manually-wired exceptions for the create/join fork.

**The create/join fork.** `obChoose(mode)` (`:58-62`) sets `FAM.mode` and either goes straight to `join` (a 6-digit code entry, `obJoin()` at `:71-75` — but note the actual redeem logic is a placeholder here too, see below) or pre-fills the profile step and goes to `profile`. A `create` flow continues profile → family (name + member roster) → budget → theme → done; a `join` flow short-circuits from profile straight to theme (`obProfileNext()`, `:87-92`, the `else` branch), since a joiner inherits the existing family's categories/budget rather than defining their own.

**`obPrefillBudget()` — a client-side mirror of a server function, by necessity.** For a `create` flow, the budget step needs to show starter categories before any category actually exists client-side (`catOrder` is empty at this point in the flow). The server will seed six default categories at `create_family()` time (`seed_default_categories()`, `supabase/migrations/0003_functions_triggers.sql:95-106`), but that RPC doesn't run until the user taps through to `done` — the budget *step*, which comes earlier in the wizard, still needs something to show sliders for. The fix is `DEFAULT_CATS` (`src/js-ui/80-onboard-boot.js:146-153`), a hardcoded array that reproduces the server's six categories — name (vi/en), emoji, color — and the comment directly above it is explicit about the risk:

> `/* The default categories a brand-new family gets. MUST mirror seed_default_categories() (0003) in the SAME ORDER — the server seeds these at create_family and createFamilyInDB attaches the budgets by sort_order → so the onboarding budget step needs them client-side (catOrder starts empty). */`

The ordering constraint is load-bearing, not cosmetic: `seed_default_categories()` inserts rows with explicit `sort_order` values 1–6 in the order Housing, Groceries, Dining, Transport, Fun, Kids (`0003_functions_triggers.sql:99-105`), and `DEFAULT_CATS` lists the same six concepts in the same order (`80-onboard-boot.js:147-152`). Later, `createFamilyInDB()` (`src/js-data/70-goals-income-onboard-ui.js:304-313`) reads the categories the server actually created back out (`select id, sort_order`) and maps each `category_budgets` row to `order[c.sort_order - 1]` — i.e., it re-derives "which budget amount goes with which category" purely by *positional index into the client's `catOrder` array*, matched against the server's `sort_order`. If the two orderings ever drifted (someone reorders `DEFAULT_CATS` without touching the SQL, or vice versa), a user's per-category budget entries would silently attach to the wrong category — e.g. money the user typed next to "Dining" landing on "Transport" — with no error, because both sides are internally consistent numeric indices, just misaligned with each other. There is no shared source of truth (no codegen, no JSON the SQL and JS both read); the comment is the only thing keeping the two declarations in sync, which is why it says "MUST" and calls it out explicitly. `_obCatConcept` (`:154`) is a secondary map (display name → underlying concept key) that exists so the auto-split proportions (`BUDGET_PROPS`, `:141`) resolve correctly regardless of whether the UI is showing Vietnamese or English category names.

**`obGoogle()` — a placeholder designed to fail loudly.** Because `src/index.html` loads `src/js-ui/*` as a classic, synchronous `<script>` block and `src/js-data/*` as a deferred `<script type="module">` (`build.js:19-20`, `src/index.html:970-981`), the onboarding markup and its inline `onclick="obGoogle()"` handlers exist and are clickable before the real Supabase auth module (`src/js-data/10-client-auth.js`) has necessarily finished loading and overwritten `window.obGoogle`. `80-onboard-boot.js:48-57` defines a stand-in:

```js
function obGoogle(){
  var b=document.getElementById('ob-gbtn');
  if(b){ b.disabled=true; ... }
  setTimeout(function(){
    if(window.obGoogle!==obGoogle){ window.obGoogle(); return; }   // real one landed → hand over
    if(b){ b.disabled=false; ...}
    toast(L('Không kết nối được máy chủ...','Can't reach the server...'));
  }, 1200);
}
```

It waits 1.2s, then checks by function identity whether the real implementation (`window.obGoogle = async function(){...}`, `src/js-data/10-client-auth.js:263-269`) has replaced it; if so it hands off by calling the new `window.obGoogle()`. If not — module blocked by CDN, offline, script error — it re-enables the button and shows an explicit "can't reach the server" toast. The comment directly above the function names the failure mode this replaced:

> `/* Placeholder only. The auth module replaces this with the real Supabase flow as soon as it loads. If it never does (offline, CDN blocked), this must NOT wave the user through: it used to advance to 'choice', let them complete every onboarding step, and then write the whole family to localStorage only — nothing reached the database and nothing said so. Failing loudly here is the honest outcome. */`

That is a concrete, previously-shipped bug: with the old placeholder, a user whose network dropped the auth module could complete the *entire* wizard — pick a family name, add members, set a budget, choose a theme — see a "Welcome!" done screen, and land on what looked like a fully working app, while every byte of it lived only in `localStorage`. No account existed; no other device or session would ever see that family; the data was one `localStorage.clear()` away from gone. The fix's design principle is narrow and specific: a placeholder function that stands in for real infrastructure must be observably a placeholder the moment it's asked to do the thing only the real infrastructure can do (reach the server) — silent success is worse than a visible failure, because a visible failure gets reported and a silent one gets discovered months later as "where did my data go." The join-code placeholder (`obCodeInput`/`obJoin`, `:63-75`) follows the identical pattern for the same reason, with its own comment explaining that it "never fakes a family."

**Handoff into the database.** `finishOnboarding()` (`:221-229`) is the client-only tail: it applies `FAM` to the live app state, sets `localStorage['fh-onboarded']='1'`, marks release notes seen for a fresh user, and calls `go('home')`. The actual account/family creation is wired in from the data layer: `src/js-data/70-goals-income-onboard-ui.js:332-354` wraps `window.finishOnboarding` (saving the original as `_origFinish`) so that tapping "Enter FamilyHub" first `await`s `createFamilyInDB()` (create flow) or `joinFinalizeDB()` (join flow), and only calls through to the original UI-only `finishOnboarding()` on success — a thrown error instead re-enables the button and toasts, leaving the user on the `done` step so their answers aren't lost. This is also where the family's origin data actually gets persisted:
- `createFamilyInDB()` (`src/js-data/70-goals-income-onboard-ui.js:236-315`) calls the `create_family` RPC, updates the owner's `members`/`profiles` rows with the name/color/theme/language chosen in the wizard, and — for a brand-new (`create`) family — generates its encryption key material: `FHCrypto.genCard()` + `genSaltHex()` + `deriveKeys()` + `genDekRaw()` + `wrapDek()`, then `init_family_card` RPC (`supabase/migrations/0043_family_card_birth.sql:22`) to atomically create the family's `enc` row and its first `family_key_wraps` entry, then `fhKeyAdopt()` to load the DEK into the session (`:268-280`). This is wrapped in its own `try/catch` with an explicit degrade-gracefully comment: a failure here does not abort family creation, it just toasts that the "family code" couldn't be created and can be made later from Settings (`:281-284`). Budget writes (`monthly_budgets`, `category_budgets`) run *after* this block specifically so that, when the card setup succeeds, they go through `fhField()` as ciphertext from the first write — see `docs/features/encryption.md`.
- The category-to-budget attach step (`:304-313`) is the consumer side of the `DEFAULT_CATS`/`seed_default_categories()` ordering contract described above: it re-reads categories by `sort_order` and indexes into `window.catOrder` to find each one's user-entered amount.
- `joinFinalizeDB()` (`:318-330`) is much smaller — a joiner doesn't create anything, just updates their own `members`/`profiles` row in the family they already redeemed a code into (the redeem itself happens earlier, at `obJoin()`'s real implementation in `src/js-data/65-passcode-ui.js`, not in this file).

### Boot orchestration

**Layering, earliest to latest.** Three layers run in sequence on every load, in different execution contexts:
1. **Pre-paint gate**, inline in `<head>` (`src/index.html:25-47`), runs before any CSS or the rest of the body parses. If `localStorage['fh-resume']==='1'` (set once a session has ever been established, `fhResumeArm()` in `src/js-data/10-client-auth.js:20`), it adds `.fh-resume` to `<html>` so the markup's default (onboarding-screen) state is suppressed in favor of a splash — plus a 10s watchdog in case the module never arrives. If a `fh-snap` localStorage snapshot also exists, it adds `.fh-warm-boot` so the splash itself can be skipped in favor of the cached data once it's applied.
2. **`src/js-ui/80-onboard-boot.js`**, the classic synchronous script — runs `obInit()`, `fhRestoreSnapshot()`, wires deep links, connectivity, and service-worker listeners (all detailed below), *before* the deferred data module has necessarily executed.
3. **`src/js-data/*` module**, deferred — does the actual `getSession()` / `my_families` RPC / `loadFamilyData()` hydrate, which is the ground truth that eventually supersedes whatever the snapshot painted.

**Warm-start snapshot (`fhSaveSnapshot` / `fhRestoreSnapshot`).** The problem statement is in the comment at `80-onboard-boot.js:252-258`: a full DB hydrate needs a module import plus roughly ten network round-trips, so without a cache a signed-in user stared at a splash on every single launch. The fix is a serialized copy of the app's in-memory state (`FAM`, `membersMeta`, `catOrder`/`catStyle`/`catBudget`, `txns`, `months`, `events`, `savings`, `LANG`/`CUR`, and a snapshot of `window.DB`) written after every successful hydrate and replayed synchronously before the first paint on the next launch — "cache is display state only; it is never trusted for writes" (`:255-256`), because the real hydrate's DB-sourced maps replace it wholesale once it lands.

- **Versioning.** `FH_SNAP_V = 2` (`:262`). The comment immediately above explains what v1 broke: `// v1 snapshots cached expired *signed* photo URLs, which would warm-boot into broken images now that photos resolve to stable public URLs. Bumping discards them — one cold start for existing users, then clean.` `fhRestoreSnapshot()` (`:287-306`) checks `s.v!==FH_SNAP_V` and discards a version mismatch outright (falls through to a cold hydrate) rather than attempting any migration — the versioning contract here is "wrong version means throw it away," not "wrong version means upgrade it in place."
- **Save coalescing.** `fhSaveSnapshot()` (`:264-286`) is a no-op if called within 2500ms of its last real write (`:268`) — necessary because `loadFamilyData()` calls it unconditionally at the end of every hydrate (`src/js-data/30-hydrate.js:381`), and hydrate itself runs often (on focus, on realtime events, after nearly every write), so without coalescing a large family would re-serialize (and, for the IndexedDB tier, re-write) on every tick. Warm-boot data being a few seconds stale is an accepted tradeoff.
- **Storage tiering.** The actual write goes through `window.fhSnapStore` if the module has loaded (`src/js-data/17-snap-restore.js:36-62`), falling back to a bare `localStorage.setItem` only if that module hasn't arrived yet (`80-onboard-boot.js:283-284`). The tiering logic: small + plaintext (`≤ 1.2MB` serialized, `_SNAP_LS_MAX`, `17-snap-restore.js:22`) goes to `localStorage['fh-snap']` for a synchronous, no-splash restore; anything larger, or *any* committed-`enc` family regardless of size, spills to IndexedDB (store `fh-snap`/`snap`/`current`) with a small marker (`localStorage['fh-snap-idb']`) so the sync boot path knows to defer to the module's async restore. Encrypted snapshots are written as a v3 AES-GCM envelope (`fhEnc(JSON.stringify(data))`) — plaintext family data never touches disk for an encrypted family, even in the cache.
- **Restore paths.** `fhRestoreSnapshot()` (called synchronously at `80-onboard-boot.js:331`, before first render) handles only the localStorage-plaintext case directly, returning `true`/`false` for "did we warm-start synchronously." A legacy v3-encrypted envelope found in `localStorage` (pre-IndexedDB-spill data) or an IndexedDB-tier marker is stashed on `window.__fhSnapEnc` / `window.__fhSnapIdb` for the data module's `_snapAsyncRestore()` (`src/js-data/17-snap-restore.js:79-110`) to pick up once it's loaded — that path can decrypt (needs the cached DEK) and merges into `window.DB` without clobbering a hydrate that already landed. `fhApplySnapshot(s)` (`80-onboard-boot.js:309-320`) is the shared apply function both the sync and async paths call, and it's the one place `Date` objects get reconstituted from the epoch-ms form `fhSaveSnapshot()` stored them in.
- **Applying the snapshot at boot** (`:330-338`): if `fhRestoreSnapshot()` returned `true`, the code immediately calls `applyFam()`/`applyLang()`, marks onboarding `.done`, and adds both `fh-warm` and `fh-stale` classes to `<html>` — `fh-stale` drives a persistent "Updating…" chip until `window.fhFresh()` (`:324`, called from the real hydrate at `30-hydrate.js:366`) removes it. If restore returned `false` (no cache, or version mismatch), the `fh-warm-boot` class is removed so the splash covers the still-showing mock/demo data in `FAM`'s hardcoded defaults (`:2-7`) instead of flashing it.

**Service-worker update lifecycle.** The stated policy (`80-onboard-boot.js:392-398`) changed from "reload on update" to "wait and let the user (or an idle moment) decide": a new build installs and sits in `reg.waiting` rather than force-activating, because a mid-session reload was disruptive. `navigator.serviceWorker.register('sw.js')` (`:434-448`) wires `updatefound` → if a worker reaches `installed` state *while a controller already exists* (i.e., this is a real update, not the very first install — `:440`), it calls `fhUpdateReady(reg)` (`:400-403`), which adds `.fh-newver` to reveal an update chip. Two ways the update actually applies:
- **User-initiated** — `fhApplyUpdate()` (`:404-411`) sends `{type:'SKIP_WAITING'}` to `reg.waiting`; the SW activates, `controllerchange` fires, and (since `hadController` was true — this isn't the first-ever install, `:428-433`) the page reloads into the new build.
- **Auto-applied when backgrounded** — `fhMaybeAutoSwap()` (`:417-424`), called from `visibilitychange` when the tab goes hidden (`:446`). It only fires the swap if **all** of: no update is already mid-swap (`__fhSwapping`); a waiting worker actually exists; `window.editingTx` is `null` (nothing mid-edit in the expense-capture flow); no `.sheet.on`/`.modal.on`/`.overlay.on` is open (no bottom sheet or modal currently showing, which would visually reset on reload); and `window.fhOutboxEmpty()` resolves `true` (`src/js-data/40-txn-writes-outbox.js:256` — no queued offline write still sitting in the IndexedDB outbox waiting to sync). The intent of stacking all four checks is that the user should never come back to a reload that dropped something they were doing — they should simply return to find the app already on the new build, no chip, no interruption. There is a documented exception to "wait, don't force": `_fhEncRecover()` (`src/js-data/65-passcode-ui.js:49-69`) forces an immediate `SKIP_WAITING` (bypassing the wait/background-only policy) to self-heal a client that's running a build stale enough to be issuing encryption-guard errors — see `docs/features/encryption.md` for when that recovery path triggers.
- `navigator.storage.persist()` is requested on load (`:427`) specifically so the offline outbox and cached crypto keys aren't evicted under storage pressure — losing either silently would mean a lost write or a forced re-unlock.

**Deep-link hash routing.** A small IIFE (`:367-378`) reads `location.hash` once at boot and routes a handful of shapes (`#event-<id>` → open that event, `#sheet-<id>` → open that sheet, `#overview`/`#budget`/`#breakdown`/`#member`/`#activity`/`#tx`/`#memories`/`#events`/`#home`/`#spending`) to the corresponding screen/segment via `go()`/`segTo()`/`openEvent()`/`openSheet()`. This runs once, synchronously, as part of the classic-script boot sequence — before the data module's hydrate — so a shared link opens on the right screen even before real data has loaded.

**Connectivity flag.** `fhSyncOnline()` (`:383-390`) toggles a `.fh-offline` class on `<html>` from the browser's `online`/`offline` events, and — when transitioning back online with a family already open — calls `loadFamilyData()` to catch up. The comment at `:380-382` frames why this matters: writes in this app are optimistic and fire-and-forget, so if the UI didn't visibly flag offline, someone could log a whole evening's expenses believing they saved, with nothing actually leaving the device.

## Current State

Production-complete; both halves show heavy iteration rather than a first pass, and each leaves a comment naming the specific prior bug it exists to prevent:
- The `obGoogle()` fail-loudly placeholder (`80-onboard-boot.js:43-57`) replaced a version that silently let a user complete the entire wizard into `localStorage`-only state, never reaching the database, with no error surfaced — see quote above.
- The snapshot cache is on its second format (`FH_SNAP_V=2`, `:259-262`): v1 cached signed (expiring) photo URLs and would warm-boot into broken images; the version bump forces a one-time cold start for existing users rather than attempting a migration.
- The passcode step was retired from the wizard entirely (`obOrder` comment at `:10`: "'passcode' retired — new families are born on the Key Card (0043), introduced after onboarding") in favor of every new family being born directly on Key Card–based encryption (`0043_family_card_birth.sql`), with the card generated inside `createFamilyInDB()` and introduced to the user via a dedicated post-onboarding screen (`window.__fhNewCard` / `fhCardShow`, `src/js-data/70-goals-income-onboard-ui.js:280,349-353`) rather than during the wizard.
- Service-worker update behavior changed from immediate-reload to wait-and-batch (`fhMaybeAutoSwap`'s four safety conditions), with a separate forced-swap escape hatch (`_fhEncRecover`) added later for one specific failure mode.
- `DEFAULT_CATS` (client) and `seed_default_categories()` (server, `0003_functions_triggers.sql:95-106`) are independently maintained and verified here to currently agree — six categories, same order — but nothing enforces that agreement automatically; it is a documented manual invariant, not a generated one.

No open TODOs or known gaps were found in this file; the comments throughout read as postmortems for shipped-and-fixed bugs, not as flags for unfinished work.
