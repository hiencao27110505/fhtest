# Social Alignment: Reactions & Requests

## Problem & Why

FamilyHub's ledger is shared by design — every member sees every other member's spending, goals, and plans. That creates two distinct social needs that look similar on the surface but solve opposite problems:

1. **React to something that already happened.** A member sees a transaction another member logged and wants to respond emotionally — surprise, amusement, approval, annoyance — without it meaning anything beyond "I saw this and felt something." Low stakes, no consequence, purely expressive.
2. **Get buy-in before something happens.** A member wants to propose a future expense, a savings goal, or an upcoming occasion, and — because it will draw on shared family money — that proposal shouldn't count toward the family's plans until at least one *other* member has actually said yes. High stakes: alignment gates whether the proposal reserves money at all.

Both features reuse the exact same five emoji — 😱🤨😂🥰😤 (`RX`, `src/js-ui/62-reactions.js:8-14`; re-declared as `_reqReviewSet()`, `src/js-ui/64-requests.js:27-33`). That's a deliberate product choice — the family already has shared vocabulary for these five glyphs, so reusing them lowers the cognitive cost of a second feature — but it means the same UI control means two unrelated things depending on where it's tapped from. In Reactions, all five are equally valid free-form expression; there is no "correct" emoji. In Requests, the five are re-labeled as consent language (see the `dvi`/`den` decision-subtitles below), and exactly one of them — 🥰, and only when it comes from someone other than the person who proposed it — changes system state. The other four are feedback that does nothing structurally. An engineer who assumes "emoji picker" implies "reactions" anywhere in this codebase will misread half of these call sites.

The two systems are also strictly partitioned by time, enforced in code, not just convention: Reactions only apply to **realized** transactions (already happened, `!t.future`); Requests only apply to **unrealized** proposals (`t.future === true` for expenses, plus not-yet-achieved goals and future-dated occasions). `_rxWallItems()` explicitly filters out future rows with the comment "reactions on a future expense are REVIEWS, a separate feature" (`src/js-ui/62-reactions.js:201`). A transaction literally changes feature ownership the moment its date passes from future to today — same row, same emoji picker markup, different subsystem underneath.

## Architecture & How It Works

### Reactions

**Vocabulary and message generation.** `RX` (`src/js-ui/62-reactions.js:8-14`) is a fixed array of five `{k, e, vi, en}` reaction configs. `RX_MSG` (`:17-33`) holds a small pool of localized one-liner templates per emoji (e.g. 😱 → "{n} đang xỉu ngang vụ này" / "{n} is losing it over this"), with `{n}` = reactor first name and `{cat}` = transaction category. `rxMessage()` (`:41-47`) picks one line from the pool deterministically via `rxHash()` (`:35`), a simple string hash over `txId|memberId|emoji` — so re-rendering the same reaction (on refresh, on another device) always produces the same sentence instead of reshuffling on every render.

**Cardinality: one reaction per (transaction, member).** Enforced twice: client-side, `_rxLocalSet()` (`:124-134`) filters out the member's prior reaction on that transaction before appending the new one; server-side, `unique (transaction_id, member_id)` plus upsert-on-conflict (`supabase/migrations/0023_reactions.sql:25`, `36-37` write path in `src/js-data/50-writethrough-realtime.js:334-336`). Re-reacting **replaces**, it never stacks. Tapping your own currently-set emoji again clears it (the `remove` branch in `throwReaction()`, `62-reactions.js:137-138`).

**Entry point.** A long-press (460ms hold, 12px move tolerance, both touch and mouse event models, bound once via delegation at the bottom of the file, `62-reactions.js:155-185`) on any `.row[data-rxid]` opens `openRxPicker()` (`:71-98`), a small popover of the five emoji anchored to the press point, flipping to appear below the finger if there isn't room above.

**Throw path.** `throwReaction(txDbId, emoji)` (`:135-150`) is optimistic: it updates local state immediately (`_rxLocalSet`), fires a small local particle burst from the exact point pressed (`rxBurst()`, `:104-121` — distinct from the full-screen "arrival" animation described below, which is what the *other* member sees), then persists via `window.fhReact()` (async, `src/js-data/50-writethrough-realtime.js:327-343`), which upserts into the `reactions` table and calls `fhNotify('reaction', {emoji, tx})` to nudge other family members' closed-app devices via Web Push.

**Three surfaces**, per the file's own header comment:
- **(A) Inline chip** on the ledger row — `rxChip()` (`:60-67`): the set of unique emoji on that transaction plus the latest reaction's message and a `+N` count for additional reactors.
- **(B) The "Phòng khách" (living room) wall** — `renderRxWall()` (`:225-233`), fed by `_rxWallItems()` (`:196-207`): one card per transaction that has at least one reaction, newest lead-reaction first. This is the function that enforces the realized-only boundary — it explicitly skips any `tx.future` row (`:201`), which is the concrete code line marking the Reactions/Requests split.
- **(C) The arrival** — `rxCheckArrivals()` (`:258-272`): fires for *any* other member's reaction on a realized transaction, not just reactions on your own spends. Watermark-gated via `localStorage['fh-rx-seen']` (`_rxSeen`/`_rxSetSeen`, `:248-249`): the first run seeds the watermark without replaying history; subsequent runs diff `window.reactions` against the watermark to surface only genuinely new reactions, filtering out the viewer's own reactions and future-txn reviews. `rxArriveShow()` (`:276-293`) is deliberately non-blocking — full-frame emoji confetti plus a tappable, auto-dismissing (5.6s) toast that deep-links to the transaction — suppressed only while a full-screen celebration or the onboarding overlay is up (`_rxBusy()`, `:250-257`).

**Persistence.** `reactions` table (`supabase/migrations/0023_reactions.sql:17-31`): `unique (transaction_id, member_id)`, composite FK to `transactions(id, family_id)` mirroring `transaction_photos`, family-scoped RLS, added to the realtime publication, and spliced into the `get_family_snapshot()` hydrate payload in the same migration (`0023_reactions.sql:130-133`). Hydrate builds `window.DB.reactionsByTx` (grouped by transaction) and a flat, newest-first `window.reactions` feed that both the wall and the arrival check read (`src/js-data/30-hydrate.js:250-262`).

### Requests

**One shape, three entity types.** A proposal can be a future expense, a savings goal, or a future occasion. `_entNorm(type, obj, ref)` (`src/js-ui/64-requests.js:49-56`) normalizes any of the three into one common shape: `{type, ref, dbId, key, obj, title, amount, icon, dateTxt, creatorId, reviews}`. The field mapping differs per type (expense: `obj.amt`/`obj.note`/`obj.ico`; goal & occasion: `obj.target`/`obj.name`/`obj.emoji`, falling back to type-level icon/copy from `_entMeta()`, `:38-42`), but every downstream card, widget, and review sheet in this file operates on the normalized shape and never branches on `type` except where the label genuinely differs.

**Who proposed it vs. who pays.** `creatorId` comes from `_entCreatorId(type, obj)` (`src/js-ui/10-nav-model.js:67`): `obj._createdBy || obj.by || obj._by || null`. This is the *requester*, and it is a distinct concept from the payer/owner (`member_id` on a transaction, the goal's contributor, etc.) — a family member can propose an expense that a different member ends up paying. Persistence for this is a `created_by` column added to **three** tables — `transactions`, `saving_goals`, `events` — in the same migration that introduces the review mechanism (`supabase/migrations/0024_requests.sql:13-15`). Per that migration's own header comment, `0024` was **applied to production (fhtest) via Supabase MCP on 2026-08-01** (`0024_requests.sql:9`).

**Reviews.** `_entReviews(type, dbId, obj)` (`src/js-ui/10-nav-model.js:68-78`) resolves a proposal's review list: it prefers a local optimistic `obj._reviews`/`obj.reviews` (freshly submitted, or demo-seed data), and otherwise reads `window.DB.reviewsByEntity[type + ':' + dbId]`, populated at hydrate time from the polymorphic `request_reviews` table (`src/js-data/30-hydrate.js:264-272`). That table has one row per `(entity_type, entity_id, member_id)` — `entity_type in ('expense','goal','occasion')` — unique-constrained the same way `reactions` is unique per `(transaction_id, member_id)` (`supabase/migrations/0024_requests.sql:20-30`), so re-reviewing **replaces**, exactly mirroring the Reactions replace-not-stack rule.

**The review vocabulary re-labels the same five emoji for consent, not emotion.** `_reqReviewSet()` (`64-requests.js:27-33`) is the same 🥰😂😱🤨😤 set, but each entry carries a `dvi`/`den` decision-subtitle instead of an emotion label — e.g. 🥰 is captioned "Đồng ý — chốt luôn" / "I'm in — count me", 😤 is "Chưa hợp lúc này" / "Not right now". None of the five copy pairs read as "I feel X about this"; they all read as a decision on the proposal.

**Alignment: only 🥰, only from someone else.** `_entAligned(item)` (`64-requests.js:57`, mirrored server-adjacent as `_entAlignedBy(type, obj)` in `10-nav-model.js:79`) is `true` iff some review has `emoji === '🥰'` **and** `by !== item.creatorId`. This is the entire alignment rule — the other four emoji, and even a 🥰 from the requester themself (which the UI prevents anyway, see below), never flip this flag. Alignment has a real financial consequence: `futureAligned()` / `futurePending()` / `futureExpReserved()` (`10-nav-model.js:82-84`) mean an unaligned future expense does **not** count toward the month's reserved total — only an aligned one does. This is the mechanism the migration's header comment means by "must be reviewed and aligned... before it counts" (`0024_requests.sql:4-5`).

**The requester can never decide their own proposal.** `_isMine(item)` (`64-requests.js:59`) gates the review UI into two views from `openReview()`/`renderReview()` (`:183-243`):
- **DECIDE view** (not-mine, `:230-241`): the five re-labeled rows, uniform (no highlighted default CTA), each calling `submitReview(type, ref, emoji)`.
- **FOLLOW view** (mine, `:214-227`): read-only — an aligned/waiting banner plus the list of who responded with what. `submitReview()` also defensively closes the sheet if `_isMine(item)` somehow slips through (`:250`).

**Two split lists instead of one feed.** `reqIncoming()` / `reqMine()` / `reqPendingAll()` (`64-requests.js:77-86`) partition all proposals across the three entity types into: incoming (not mine, still pending — needs *my* review), mine (all of mine regardless of status — the thing I'm following), and pending-all (everything unaligned, others'-actionable sorted before my-own-pending, used for the Home/Finance widget's badge count). This is the "waiting for you to review" vs. "yours, waiting on others" split described in the file header.

**Write path.** `submitReview()` (`:247-271`) optimistically appends to `obj._reviews` locally, then persists via `window.fhReviewEntity(entityType, entityId, emoji)` (`src/js-data/50-writethrough-realtime.js:349-364`) — an upsert on `(entity_type, entity_id, member_id)`, the same call shape and REPLACE-not-stack semantics as `fhReact`. It then notifies **only the original requester** — `fhNotify('request_response', {emoji, target: item.creatorId, et: type, eid: obj._dbId})` (`64-requests.js:257`). This is a meaningful divergence from Reactions' push behavior: `fhReact`'s `fhNotify('reaction', ...)` call carries no `target`, so the `push-send` edge function fans it out to every other opted-in device in the family (`supabase/functions/push-send/index.ts:128-132`); `request_response` sets `target`, which the same edge function uses to narrow the recipient query to that one member (`push-send/index.ts:132`: `if (target) q = q.eq('member_id', target)`). A new proposal (`request_new`, fired from `50-writethrough-realtime.js:12` and `:167`, and `70-goals-income-onboard-ui.js:13` when a future expense/goal/occasion is created) has no target either — it fans out to everyone else, since anyone could be the one to align it.

**Dual, independent watermarks — separate from the Reactions watermark.** `reqCheckArrivals()` (`64-requests.js:278-314`) tracks two things, each with its own `localStorage` key:
- `fh-reqnew-seen` — new incoming requests, keyed by a set of `item.key` strings (`type:dbId`) rather than a single timestamp, since a proposal can be reviewed and leave the incoming list without ever producing a "newer" watermark value.
- `fh-reqdec-seen` — decisions landing on *my* requests, timestamp-watermarked like `fh-rx-seen`, but computed only over `reqMine()`'s reviews from members other than me.

Both are entirely separate from Reactions' `fh-rx-seen` — a family member can be caught up on reactions and behind on requests, or vice versa, independently.

**Persistence.** `request_reviews` table (`supabase/migrations/0024_requests.sql:20-33`): polymorphic `entity_type` + `entity_id`, unique per `(entity_type, entity_id, member_id)`, family-scoped RLS mirroring `reactions`' policies verbatim, realtime-published, and spliced into `get_family_snapshot()` alongside the new `created_by` columns in the same migration (`0024_requests.sql:96`, `102`, `126`, `132-135`).

**How Requests uses the shared entity-review pattern.** The `_entNorm` / `_entAligned` / `_entCreatorId` / `_entReviews` functions this doc has been citing from `src/js-ui/10-nav-model.js` are the general-purpose entity-review layer shared across the codebase — see `../ARCHITECTURE.md` for the pattern itself, since `docs/features/goals.md` and `docs/features/transactions.md` also consume it for goal- and expense-specific UI outside the Requests hub (e.g. a goal detail screen showing its own alignment badge). What's specific to this doc is that Requests is the feature that **exercises the pattern across all three entity types at once** — it's the only place in the app that normalizes expenses, goals, and occasions into one shape and renders them in one merged list (the two-lane hub, `renderRequests()`, `64-requests.js:169-180`). Goals and Transactions each read their own entity's alignment state directly; Requests is what makes "proposal" a first-class cross-entity concept instead of three parallel, type-specific features.

## Current State

Both Reactions and Requests are production-complete with no known gaps.

- Reactions: five fixed emoji, one-per-(transaction, member), three surfaces (inline chip, "Phòng khách" wall, cross-device arrival), watermark-gated arrivals, realized-transactions-only scope.
- Requests: three proposable entity types (expense, goal, occasion) normalized through one shared shape, consent-relabeled reuse of the same five emoji, single-emoji (🥰-from-someone-else) alignment rule with a real effect on money reservation, two-lane hub (incoming vs. mine), dual independent watermarks, targeted push for decisions vs. fan-out push for new proposals and reactions.

Architecturally, **Requests is the newest and most cross-cutting piece of the two** — migration `0024` (2026-08-01) is one release after `0023` (Reactions), and it was built *on top of* goals, transactions, and events after all three already existed as independent features. That's why it needed a normalization layer (`_entNorm`) that Reactions never required — Reactions only ever had one entity type (the transaction) to deal with.
