# Key Card Auth

## Problem & Why

FamilyHub's E2EE (`docs/features/encryption.md`) is only as strong as the secret that unwraps the family DEK. Until this feature, that secret was a 6-digit passcode shared by the family. A 6-digit code has ~20 bits of entropy: an attacker who obtains `wrapped_dek` (which we, the operator, hold) can grind all 10⁶ codes through PBKDF2 offline in roughly 30 seconds on a single GPU. Server-side rate limiting (`passcode_attempts`, `_fh_passcode_gate`) stops an *online* guesser but does nothing against an offline attacker holding the database — so "even we can't read it" was a policy promise, not a mathematical one, as long as the passcode was the wrap key.

The fix is entropy, not process: replace the 6-digit passcode with a 128-bit random **Key Card** as the input to the same key-derivation pipeline. `2^128` is unconditionally ungrindable, for every family, including one that would have picked a weak passcode. This also cleanly separates FamilyHub's two secrets that the passcode design had conflated:
- **the door** (who is allowed into the family) — now purely the Gmail whitelist + Google SSO, no typing;
- **the safe** (what can decrypt the family's data) — the Key Card, independent of who's allowed in.

A Base32, uppercase-only card also sidesteps a Vietnamese-specific hazard a human-chosen passphrase would have had: NFC vs. NFD Unicode normalization producing different bytes for the same typed diacritics, which would surface as a mysterious "wrong code" that isn't actually wrong.

The trade this accepts, and states honestly to the user: the card must now outlive every device. Memory alone can no longer recover a family that loses every phone — the same property that let a family recover a passcode from nothing is the property that let an operator grind it. Full design rationale, delivery-form decisions (text/QR/link), and the UX copy live in `KEY-CARD-AUTH-SPEC.md` (repo root); this doc covers what actually shipped and where.

## Architecture & How It Works

The card slots into the existing key hierarchy at exactly one point — as the string fed into `FHCrypto.deriveKeys()` — and changes nothing downstream. See `../ARCHITECTURE.md` for the full key-hierarchy diagram (PBKDF2 → HKDF → K_wrap → DEK → AES-GCM) shared by both passcode and card families; this section covers only what's specific to the card as an auth mechanism.

### Card format and crypto (`src/js-data/15-crypto.js`)

- `FHCrypto.genCard()` (`src/js-data/15-crypto.js:108-112`) — 128 bits from `crypto.getRandomValues`, Crockford Base32-encoded (`_b32enc`, `:30-35`), plus a 2-char CRC-16 checksum group (`_cardCheck`, `:41-42`) appended to the 26-char body. Displayed as `FH-XXXX-XXXX-…` (`_fmtCard`, `:43`). The Crockford alphabet (`_B32`, `:28`) excludes `I/L/O/U` so handwriting, phone dictation, and reading glasses can't confuse a character; `parseCard` also folds those back in on input (`_B32MAP`, `:29`).
- `FHCrypto.parseCard(input)` (`:115-128`) — accepts any typed/scanned/pasted form: strips dashes/spaces, uppercases, remaps confusable chars, length-gated prefix stripping for `FH-`/`FH2-`, then validates the checksum. Returns `{ ok, key, raw, display }` or `{ ok:false, error: 'length'|'chars'|'checksum' }`.
- `FHCrypto.deriveKeys(secret, saltHex, iters, version)` (`:49-61`) is **unchanged in signature** — it takes the card's 26-char body exactly where it used to take the 6-digit passcode. Card families pass `FH_KDF_ITERS_CARD = 600000` (`:15`) instead of the passcode-era `FH_KDF_ITERS = 310000` (`:14`); against 128 bits of input entropy the iteration count is no longer load-bearing, it's kept as free defense-in-depth.
- Because the input is now high-entropy, `K_auth` (the door-proof half HKDF also derives, info `"fh-auth-v1"`) is derived but **unused** for card families — the door is the whitelist, not a server-verified secret. `family_keys.auth_hash` stays `NULL` for card-born rows (confirmed in `0043_family_card_birth.sql:16-17` and `init_family_card`, `:37-38`).
- `FHCrypto.cardUrl(rawOrDisplay)` (`:132-138`) and `FHCrypto.parseKeyFragment(src)` (`:141-148`) implement the URL delivery form. The card lives in the URL **fragment**, never a query param — fragments aren't sent to Vercel, logged server-side, or leaked via `Referer`. Two fragment shapes are supported: the opaque `#fh-k=<base64url(display)>` (current) and a legacy readable `#fh-key=FH-…` — both parse to the same card.
- The DEK, the `iv‖ct` AES-GCM envelope shape, `fhField`/`fhRead`, and every `enc_state` trigger are untouched by this feature — it is an *auth* change, not an *encryption* change (see `docs/features/encryption.md` for that layer).

### Data model (`family_key_wraps`, migration `0042`)

Where the passcode design stored one `wrapped_dek` on `family_keys`, this feature adds `family_key_wraps` (`supabase/migrations/0042_family_key_wraps.sql:17-28`) — a table of wraps, so multiple auth kinds (`'passcode' | 'card' | 'passkey'`) can coexist per family. This is what makes non-destructive migration possible: adding a card wrap never touches the existing passcode wrap or the DEK.

- `unique (family_id, kind) where rotated_at is null` (`:30-31`) — exactly one *live* wrap per kind; a superseded wrap gets `rotated_at` stamped instead of being deleted, so history isn't lost.
- RLS: members may `select` their family's wraps (`:38-42`) — safe, because a 2¹²⁸ wrap is useless without the card. All writes go through `SECURITY DEFINER` RPCs; there is no write policy.
- `get_family_snapshot` (redefined in the same migration, `:107-197`) ships a `key_wraps` array (`:131-135`) alongside the legacy `enc` block. The client picks the `kind='card'` wrap if present, otherwise falls back to `kind='passcode'`.

Three RPCs drive the table:
- `set_family_card(p_kdf_salt, p_kdf_iters, p_kdf_version, p_wrapped_dek, p_label)` (`0042_family_key_wraps.sql:55-76`) — owner-only, retires any existing live card wrap then inserts a fresh one. Used both at Phase-C migration and (via `fhCardMigrate`) any time an owner re-runs the "upgrade" flow.
- `rotate_family_card(...)` (`:81-104`) — same shape, but any **keyed member** may call it (not owner-gated): producing a valid wrap already requires holding the raw DEK client-side, so this grants no new privilege. This is card regeneration (lost/leaked card, member offboarding).
- `init_family_card(p_kdf_salt, p_kdf_iters, p_kdf_version, p_wrapped_dek)` (`0043_family_card_birth.sql:22-46`) — the birth path for brand-new families: creates the `family_keys` row (`enc_state='enc'` immediately, no `dual` window needed since there's no history) **and** the first card wrap in one transaction. Guarded to a family with no existing `family_keys` row and no transactions yet (`:32-33`), the same "empty family" guard `set_family_passcode` used for enc-at-birth.

`0043_family_card_birth.sql` also drops the `NOT NULL` constraint on `family_keys.wrapped_dek`/`auth_hash` (`:16-17`) — a card-born family's `family_keys` row carries `enc_state` only; the real wrap lives exclusively in `family_key_wraps`.

### Client flow: card creation, cache, unlock (`src/js-data/67-card-ui.js`)

- `_fhCardWrap()` / `window.fhHasCard()` (`:13-18`) — reads `window.DB.keyWraps` (populated from the snapshot's `key_wraps`) for a live `kind='card'` entry. This single check is what routes every unlock/invite code path between card and legacy passcode behavior.
- **Local card cache** (`:28-52`) — the plaintext card is *never* sent to or stored on the server, only its wrap is. A device that has seen the card (created it, or entered it to unlock) caches the display string in its own IndexedDB (`fh-card` DB, separate from the `fh-keys` DEK cache) so "xem mã khóa" works later on that device without re-entry. `window.fhCardCacheDrop(fid)` is wired into `fhKeyDrop` (`src/js-data/15-crypto.js:197`) so the cached card leaves the device the same moment the family's DEK does (logout/leave).
- `fhCardCreate(rpcName)` (`:59-71`) — the shared creation/rotation routine: generates a card, derives `K_wrap`, wraps the *current session's* raw DEK (`_fhDekRaw`, requires an unlocked device), calls either `set_family_card` or `rotate_family_card`, then caches the card locally. The plaintext card exists in memory only at this call site.
- `fhCardUnlock(input)` (`:85-99`) — offline-capable: derives `K_wrap` from the entered card against the live wrap's stored `kdf_salt`/`iters`/`version`, attempts `unwrapDek`; a wrong card simply fails AES-GCM decryption, no network round trip needed. On success it adopts the DEK (`fhKeyAdopt`), caches the card, and fires `mark_key_unlocked` (roster telemetry) best-effort.
- Delivery actions (`:101-165`) — durable self-backup (`fhCardCopyText`, `fhCardSaveFile`, both from `_cardShown`, the card object currently on screen) and share/invite (`fhCardQrSheet` → canvas QR of `cardUrl()`, `fhCardCopyLink`). A found/leaked QR or link is only as sensitive as the DEK it unwraps — the door (whitelist) is a separate gate, per the spec's threat model (§2.2, §9.9).
- `#fh-k=` **boot landing handler** (`:321-357`, an IIFE that runs at module load, before any auth state is known) — parses the fragment via `FHCrypto.parseKeyFragment`, immediately eats it from the URL (`history.replaceState`, never left in the bar/history/share sheet), and stashes the parsed card on `window.__fhPendingCard`. If the app isn't running standalone (i.e., opened in a plain browser tab — the iOS Safari case, since the installed PWA has separate storage), it shows a light "Got your family code" handoff sheet with **Sign in with Google** (primary — the stashed card auto-applies once this session hydrates) and **Copy the code** (fallback, for someone who's about to switch to the already-installed app instead). The actual unlock-on-arrival happens later in `loadFamilyData` (`src/js-data/30-hydrate.js:393-403`): once the family + its wraps are loaded post-hydrate, if `__fhPendingCard` is set and the device isn't already unlocked, it calls `fhCardUnlock` automatically — this is what makes "scan QR → sign in → you're in, no typing" work end to end.
- **Migration flow for the existing (passcode) family**: `fhCardMigrateIntro()` (`:215-223`) is the proactive "Lock your data with your own code" sheet; tapping its CTA calls `fhCardMigrate` (`:198-210`), which runs `fhCardCreate('set_family_card')` — adding a card wrap *beside* the still-live passcode wrap, re-wrapping the same DEK, so nothing re-encrypts and no existing unlocked device is disrupted. `window.fhCardProactive()` (`:228-241`) decides whether to surface that intro: skipped if the family has no DEK yet, already has a card, was dismissed via "Để sau" within the last 5 days (`localStorage['fh-card-later']`), or the current user isn't the owner (members can't mint the first card — `set_family_card` is owner-only, unlike `rotate_family_card`). It's called once per session from the post-hydrate path (`src/js-data/30-hydrate.js:407`), 3.5s after hydrate so it doesn't compete with the initial render.
- **Passcode retirement**: `window.fhDropPasscode` (`:245-263`) is an owner-only, arm-then-confirm action calling the `drop_family_passcode` RPC (below). The client also surfaces the friendly `no_card` rejection if the server refuses.
- **Regeneration**: `window.fhCardRegenerate` (`:266-278`) — any keyed member, calls `fhCardCreate('rotate_family_card')`.

### Server-side retirement gate (`0047_drop_family_passcode.sql`)

`drop_family_passcode()` (`:10-25`) is owner-only and **refuses unless a live `kind='card'` wrap already exists** (`:18-20`, raises `no_card`) — this is what prevents an owner from ever stranding the family without any working key. On success it nulls `family_keys.wrapped_dek`/`auth_hash` (the legacy passcode wrap) and clears that family's rows from `passcode_attempts`. Note this is a **per-family, gated, owner-invoked action** — it does not touch the `passcode_attempts` table, the `_fh_passcode_gate` function, or the `join_with_passcode` RPC globally; those remain live in the schema because families that haven't migrated (or haven't yet retired their passcode) still depend on them. See Current State below for how this differs from what `KEY-CARD-AUTH-SPEC.md`'s Phase D originally described.

### Joining: whitelist-only door for card families (`0046_whitelist_join_card.sql`)

A card family's `family_keys` row has an `enc_state` but no `auth_hash` — so `join_with_passcode` can't be its door. `find_my_invite()` (`:12-32`) now returns a `card_only` flag (`k.family_id is not null and k.auth_hash is null`, `:19`) alongside the existing invite fields; `join_with_whitelist(p_family_id)` (`:34-62`) adds the invitee as a member purely on whitelist match + valid session, no code exchanged, and is itself guarded to refuse if the target family still requires a passcode (`:46`). On the client, `obJoinPrep()` (`src/js-data/65-passcode-ui.js:72-103`) reads `card_only` and hides the code-entry boxes on the join screen (`.ob-code-wrap` in `src/index.html:878`, toggled at `65-passcode-ui.js:90-91`) for card families; `obJoin()` (`:112-139`) branches to `join_with_whitelist` in that case. The invitee still needs the card itself afterward to decrypt anything — joining (the door) and unlocking (the safe) are separate steps, exactly as designed.

### Fallback routing during migration (`src/js-data/65-passcode-ui.js`)

This file is the **legacy passcode UI**, retained as-is for families that haven't migrated (or haven't retired their old wrap): first-time passcode set (`fhSetPasscode`), change (`fhChangePasscode`), and the 6-digit unlock modal (`fhPasscodeUnlockPrompt`). The single integration point with the card system is `window.fhUnlockPrompt` (`:349-355`): every caller in the app (lock bar tap, write-lock recovery, nudges) goes through this one function, which checks `fhHasCard()` and routes to `fhCardEnterPrompt()` if true, else falls back to the passcode modal. During the dual-wrap migration window, the card-entry modal itself (`67-card-ui.js:292-315`) offers a visible "Hoặc dùng mã 6 số" (or use the 6-digit code) escape hatch whenever `window.DB.enc.wrapped_dek` is still non-null — so nobody is ever stuck between migration steps before they've received the new card.

### Onboarding integration

New families never see a passcode step. `obFamilyNext()` (`src/js-ui/80-onboard-boot.js:113-124`) routes straight from the family/members screen to budget — the comment at `:122-123` is explicit that "passcode step retired." `createFamilyInDB()` (`src/js-data/70-goals-income-onboard-ui.js:261-285`) generates the card client-side (`FHCrypto.genCard()`), derives keys, generates and wraps a fresh DEK, and calls `init_family_card` in one shot right after `create_family` — before any budget/category writes, so those land ciphertext-only from the first byte. The card is stashed on `window.__fhNewCard` and shown via `fhCardShow()` from `finishOnboarding` (`:349-353`) — the proactive "USP moment" intro screen, 700ms after onboarding completes. The old mandatory 6-digit passcode screen's handler functions (`obPcInput`, `obPasscodeNext`, `80-onboard-boot.js:128-140`) are still present in the file but are dead code — no screen in the current `obOrder` (`:10`) routes to them; the `obOrder` comment confirms: `'passcode' retired`. See `docs/features/onboarding-and-boot.md` for the full onboarding flow this slots into.
