# Account Identity — a code names the provider, prose is only a label

Why the same wallet showed up three times in Tài sản, and the design that ends
the class instead of the case. Extends full-ledger T12 ("an instrument's
identity is (provider, tail); kind is editable metadata"): the *provider* half
of that pair becomes a machine key from one registry, never a spelling.

## 1. The defect class

An account row is created by `fhPersonalAccountEnsure({provider, tail, kind})`
and, until now, `provider` was prose: whatever the mail, the model or the
statement happened to print. Measured on production 2026-09-23:

- one wallet as `momo` / `ví momo` / the operator's legal name (three cards);
- one bank as `hsbc` ••0041 and `hsbc vietnam` ••0041 (two cards, split rows);
- a tail-less `ví momo` carrying 26 real transactions.

The prose varied because the sealing path *prefers* it: `worker.mjs` sealed
`extraction.source_provider || sender.provider` — the reader's free-text label
outranking the name derived from the sending domain, which the registry had
already canonicalised. The umbrella spec recorded that inversion as a defect
(§24, "the model's label wins over the sender table's"). Every alias table
after that point is a second registry undoing variance the first had already
eliminated — and Vietnamese bank names change too often for a hand list to
chase.

## 2. The design

**One registry.** `taxonomy/providers.json` — one entry per provider, keyed by
an opaque permanent `key`. Each entry: `label` (display), `kind`
(bank | wallet | gateway | broker | lender | receipt), `names[]` (spellings
seen in the wild: the "Ví X" form, the legal name, the long bank form),
`bins[]` (NAPAS BINs, statements), `codes[]` (wallet-statement bank codes,
the `vcb` of `vcb01.09.bank`). Generated by `tools/gen-providers.js` (run by
`build.js`, the taxonomy pattern) into
`supabase/functions/_shared/mailbox/providers.mjs` and
`src/js-ui/09-providers.js` — so device and worker cannot drift. Domains stay
in `senders.mjs` for now; a test pins every domain's provider label to a
registry entry, so the two lists cannot diverge (moving the domains into the
JSON is later, mechanical work).

**Codes outrank prose, prose resolves through the registry.** In order:
sender domain (email) → NAPAS BIN / bank code (statements) → `names[]` lookup
(counterparty banks named only in text) → the shape rules (strip Ngân
hàng/TMCP, company prefixes, trailing Việt Nam) as the last resort for prose
the registry has never seen. A phrase on the deny list ("ngân hàng liên kết",
"ví", "tài khoản"…) resolves to nothing, and nothing never creates an account.

**The domain wins at sealing.** `worker.mjs` seals
`sender.provider || extraction.source_provider` — flipped. The reader's label
survives only where no sender matched (an `/ingest` row from an unknown
domain). Dedup gets *more* stable: `canonicalProvider` was absorbing the
variance downstream anyway.

**Accounts store the key.** `personal_accounts.provider_key` (0150), written
on create, matched on by `ensure()`; existing rows backfilled through the same
resolver. `provider` stays as the display label and stops being identity. A
row whose prose resolves to no key keeps `provider_key` null and matches by
label as before — an unknown provider is not worse off than today.

**People can merge what the machine gets wrong anyway.** The account sheet
gains "Gộp vào tài khoản khác": pick the account it duplicates, arm-then-
confirm naming the consequence ("N khoản chuyển sang …"), rows re-tagged
atomically, the empty card deleted. Refused across the investment /
non-investment line and when either side is the other's own kind conflict a
person should see. No auto-merge exists anywhere: a duplicate is visible and
cheap, a wrong merge is silent and wrong (§5 P7) — this is the safety net for
whatever the registry cannot know, and it removes the last reason a duplicate
needs an operator with SQL.

## 3. What must not change

- Sealed rows are immutable; old rows carry old spellings and the *device*
  resolver folds them at read time, exactly as it already does.
- `dedup_fp` never contained the provider; the clear `source_provider` column
  keeps its name and meaning, only its source is now stable.
- The forwarding `.gs` is untouched (no users; the courier work supersedes it).
- No `EXTRACTION_LOGIC_VERSION` bump, no template invalidation: templates
  freeze `source_provider` as a static, and `_tidy`'s `canonProviderName` has
  always healed those at read time; it now heals through the registry.

## 4. Failure modes

| Case | Behaviour |
|---|---|
| Prose the registry has never seen | shape rules → a stable slug; worst case a duplicate, visible, mergeable by hand |
| Two banks share a last-4 | unchanged: identity is (key, tail), so they never fold |
| A BIN or code table entry is wrong | a lost match, never a wrong one — codes only ever *narrow* |
| The generated files drift from the JSON | impossible by construction: `build.js` regenerates on every assembly, and `npm run check` fails on a stale build |
| A merge picked the wrong target | the person sees the union immediately (the card names both sources' rows); a second merge cannot undo — the confirm sheet says so before the tap |

## 5. Decision log

| # | Decision |
|---|---|
| P1 | The provider half of an instrument's identity is a registry KEY. Prose is a label. Extends T12; nothing about (…, tail) changes. |
| P2 | One registry file, generated into both runtimes by the established taxonomy pattern. Domains remain in `senders.mjs`, pinned to registry labels by test, migrated later. |
| P3 | At sealing, the sender-domain-derived provider outranks the reader's label. The label is the fallback for unknown senders only. |
| P4 | Resolution order: domain → BIN/bank code → `names[]` → shape rules → deny list → nothing. Nothing never creates an account. |
| P5 | `personal_accounts.provider_key` (0150), backfilled once through the resolver; `ensure()` matches on it; `provider` becomes display-only. |
| P6 | The 2026-09-23 alias and deny tables move into the registry as `names[]` and the deny list; the device wrappers stay as thin lookups so no caller changes. |
| P7 | Merging accounts is a human act with a named consequence. Auto-merge (the number outranking the name across providers) is REJECTED: it trades a visible duplicate for a silent wrong merge. |
| P8 | BIN and bank-code tables ship only for providers verified against real data or NAPAS's published list; an unverified code is omitted, because a missing match costs a tap and a wrong one costs an account. |
